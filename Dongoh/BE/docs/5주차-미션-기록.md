## 2. ERD 설계

### 요구사항 정리

- 사용자는 이메일과 닉네임으로 가입한다. 둘 다 중복 불가.
- 사용자는 TMDB의 특정 영화에 별점(1~5)과 코멘트를 남길 수 있다.
- 한 사용자는 여러 개의 평점을 남길 수 있다. (Member : Rating = 1 : N)
- 사용자는 영화를 즐겨찾기에 등록/해제할 수 있다. 같은 영화 중복 등록 불가.
- 영화 자체의 상세 정보는 우리 DB에 저장하지 않는다.

### 엔티티와 관계

| 엔티티 | 역할 |
| --- | --- |
| Member | 회원 |
| Rating | 평점 (Member : Rating = 1 : N) |
| Favorite | 즐겨찾기 (8주차에 사용, 이번엔 스키마만) |

**`movie_id`를 FK로 걸지 않은 이유**
Rating과 Favorite이 가리키는 영화는 TMDB의 데이터이지 우리 DB의 테이블이 아니다. 그래서 외래키가 아니라 TMDB 식별자를 그대로 담아두는 일반 컬럼으로 뒀다.

**복합 UNIQUE를 건 이유**
`(member_id, movie_id)` 조합에 UNIQUE를 걸면 "한 사람이 같은 영화에 평점을 두 번 남기는 것"을 DB 차원에서 막을 수 있다. 애플리케이션 코드에서 중복 검사를 해도 동시 요청이 들어오면 둘 다 통과할 수 있는데, DB 제약은 그런 경우에도 확실하게 막아준다.

### 테이블 생성 SQL

```sql
CREATE DATABASE umc_movie;
USE umc_movie;

CREATE TABLE member (
    member_id   BIGINT AUTO_INCREMENT PRIMARY KEY,
    email       VARCHAR(254) NOT NULL UNIQUE,
    password    VARCHAR(60)  NOT NULL,
    nickname    VARCHAR(50)  NOT NULL UNIQUE,
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

CREATE TABLE rating (
    rating_id   BIGINT AUTO_INCREMENT PRIMARY KEY,
    member_id   BIGINT   NOT NULL,
    movie_id    BIGINT   NOT NULL,
    score       TINYINT  NOT NULL,
    comment     TEXT,
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (member_id) REFERENCES member(member_id),
    UNIQUE KEY uk_rating_member_movie (member_id, movie_id)
);

-- 8주차 즐겨찾기 실습용. 이번 주차에는 스키마만 만들어 둔다.
CREATE TABLE favorite (
    favorite_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    member_id   BIGINT   NOT NULL,
    movie_id    BIGINT   NOT NULL,
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (member_id) REFERENCES member(member_id),
    UNIQUE KEY uk_favorite_member_movie (member_id, movie_id)
);
```

**컬럼 길이의 근거**

- `email VARCHAR(254)` — 이메일 주소 최대 길이는 RFC 5321에서 254자로 정의
- `password VARCHAR(60)` — bcrypt 해시는 항상 정확히 60자

## 3. API 명세

| API | Method | URL | Request | Success Response (200) |
| --- | --- | --- | --- | --- |
| 닉네임 중복 체크 | GET | `/members/nickname/{nickname}` | Path: nickname (string) | `{ "available": true }` |
| 이메일 중복 체크 | GET | `/members/email/{email}` | Path: email (string) | `{ "available": true }` |
| 유저별 평점 조회 | GET | `/members/{memberId}/ratings` | Path: memberId (number) | `[{ "ratingId": 1, "movieId": 550, "score": 5, "comment": "최고의 영화!", "createdAt": "...", "updatedAt": "..." }]` |

### 명세를 쓰면서 짚은 것

**`available`의 의미**
"가입에 쓸 수 있는가"를 뜻한다. DB에 이미 있으면 못 쓰는 것이므로, 서비스 코드에서 `!exists`로 뒤집어서 내려준다.

| 상황 | exists | available |
| --- | --- | --- |
| 이미 쓰는 닉네임 | true | false |
| 아무도 안 쓰는 닉네임 | false | true |

**유저별 평점 조회는 왜 배열인가**
한 사용자가 여러 평점을 남길 수 있으므로(1:N) 응답은 항상 목록이다. 평점이 하나도 없으면 빈 배열 `[]`이 나간다.

**없는 유저는 왜 404인가**
존재 확인을 안 하면 999번처럼 없는 유저도 `[]`를 받는다. 그러면 프론트 입장에서 "평점을 안 남긴 유저"와 "없는 유저"가 구분되지 않는다. 그래서 404로 명확히 구분했다.

## 4. 핵심 코드

### Entity

```java
// entity/BaseTimeEntity.java
package com.umc.movie.entity;

import jakarta.persistence.Column;
import jakarta.persistence.MappedSuperclass;
import lombok.Getter;
import org.hibernate.annotations.CreationTimestamp;
import org.hibernate.annotations.UpdateTimestamp;

import java.time.LocalDateTime;

@Getter
@MappedSuperclass
public abstract class BaseTimeEntity {

    @CreationTimestamp
    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @UpdateTimestamp
    @Column(name = "updated_at", nullable = false)
    private LocalDateTime updatedAt;
}
```

`@MappedSuperclass`는 그 자체로 테이블이 되지는 않지만 상속하는 자식 엔티티에게 컬럼 정의를 물려준다. Member/Rating/Favorite 세 엔티티가 모두 같은 시각 컬럼을 가지므로 공통 부모로 뽑았다.

```java
// entity/Member.java
package com.umc.movie.entity;

import jakarta.persistence.*;
import lombok.AccessLevel;
import lombok.Getter;
import lombok.NoArgsConstructor;

@Entity
@Table(name = "member")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Member extends BaseTimeEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "member_id")
    private Long memberId;

    @Column(nullable = false, unique = true, length = 254)
    private String email;

    @Column(nullable = false, length = 60)
    private String password;

    @Column(nullable = false, unique = true, length = 50)
    private String nickname;

    public Member(String email, String password, String nickname) {
        this.email = email;
        this.password = password;
        this.nickname = nickname;
    }
}
```

```java
// entity/Rating.java
package com.umc.movie.entity;

import jakarta.persistence.*;
import lombok.AccessLevel;
import lombok.Getter;
import lombok.NoArgsConstructor;

@Entity
@Table(name = "rating", uniqueConstraints = @UniqueConstraint(columnNames = {"member_id", "movie_id"}))
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Rating extends BaseTimeEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "rating_id")
    private Long ratingId;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "member_id", nullable = false)
    private Member member;

    @Column(name = "movie_id", nullable = false)
    private Long movieId;

    @Column(nullable = false, columnDefinition = "TINYINT")
    private Integer score;

    @Column(columnDefinition = "TEXT")
    private String comment;
}
```

`movieId`는 TMDB 식별자라 `@ManyToOne`이 아니라 일반 `@Column`이다. Member만 우리 DB 안의 관계라서 연관관계로 매핑했다.

package com.umc.movie.repository;

import com.umc.movie.entity.Rating;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.List;

public interface RatingRepository extends JpaRepository<Rating, Long> {

메서드 이름만으로 쿼리가 만들어지는 Query Method를 썼다. `findByMember_MemberId`는 "Rating의 member 필드를 타고 들어가서 그 안의 memberId로 찾아라"는 뜻이고, `OrderByRatingIdDesc`가 최신순 정렬을 붙여준다.

package com.umc.movie.dto;

import com.umc.movie.entity.Rating;

import java.time.LocalDateTime;

public record RatingResponse(
        Long ratingId,
        Long movieId,
        Integer score,
        String comment,

    public static RatingResponse from(Rating rating) {
        return new RatingResponse(

**엔티티를 그대로 응답하지 않은 이유**
`Rating` 엔티티에는 `member` 필드로 Member 객체가 통째로 들어 있고, Member에는 `email`과 `password`가 있다. 그대로 내보내면 비밀번호 해시까지 JSON에 실려 나간다. 게다가 `fetch = LAZY`라서 직렬화 중에 예외가 터지기도 한다. 그래서 `RatingResponse`에는 `member`를 아예 빼고 필요한 필드만 담았다.

### Service

```java
// service/MemberService.java
package com.umc.movie.service;

import com.umc.movie.dto.EmailCheckResponse;
import com.umc.movie.dto.NicknameCheckResponse;
import com.umc.movie.repository.MemberRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@RequiredArgsConstructor
public class MemberService {

    private final MemberRepository memberRepository;

    @Transactional(readOnly = true)
    public NicknameCheckResponse checkNickname(String nickname) {
        boolean exists = memberRepository.existsByNickname(nickname);
        return new NicknameCheckResponse(!exists);
    }

    @Transactional(readOnly = true)
    public EmailCheckResponse checkEmail(String email) {
        boolean exists = memberRepository.existsByEmail(email);
        return new EmailCheckResponse(!exists);
    }
}
```

```java
// service/RatingService.java
package com.umc.movie.service;

import com.umc.movie.dto.RatingResponse;
import com.umc.movie.repository.MemberRepository;
import com.umc.movie.repository.RatingRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.server.ResponseStatusException;

import java.util.List;

@Service
@RequiredArgsConstructor
public class RatingService {

    private final RatingRepository ratingRepository;
    private final MemberRepository memberRepository;

    @Transactional(readOnly = true)
    public List<RatingResponse> getRatingsByMember(Long memberId) {
        if (!memberRepository.existsById(memberId)) {
            // @RestControllerAdvice로 예외를 한 곳에서 다루는 방법은 6주차에 배운다.
            // 지금은 Spring이 기본 제공하는 ResponseStatusException으로 404를 바로 응답한다.
            throw new ResponseStatusException(HttpStatus.NOT_FOUND, "존재하지 않는 유저입니다.");
        }

        return ratingRepository.findByMember_MemberIdOrderByRatingIdDesc(memberId).stream()
                .map(RatingResponse::from)
                .toList();
    }
}
```

**MemberService에 합치지 않고 RatingService를 따로 둔 이유**
URL은 셋 다 `/members`로 시작하지만, 평점 조회가 실제로 다루는 테이블은 `rating`이다. `memberId`는 필터 조건일 뿐이다. 6~8주차에 평점 CRUD와 즐겨찾기가 붙으면 메서드가 계속 늘어날 텐데, 그때 가서 분리하려면 컨트롤러와 테스트까지 같이 손봐야 한다. 자원 기준으로 미리 나눠 뒀다.

## 5. CORS 설정

### SOP와 CORS

브라우저에는 **동일 출처 정책(Same-Origin Policy)** 이라는 기본 보안 규칙이 있다. 출처는 **프로토콜 + 호스트 + 포트**의 조합이고, 셋 중 하나라도 다르면 다른 출처다.

```
http://localhost:5173   프론트엔드
http://localhost:8080   백엔드       ← 포트만 달라도 다른 출처
```

**CORS(Cross-Origin Resource Sharing)** 는 서버가 응답 헤더에 "이 출처에서 오는 요청은 허용한다"고 표시해주는 약속이다. 브라우저는 그 헤더를 확인하고 나서야 응답을 자바스크립트에 넘겨준다.

**중요한 건 요청 자체는 서버에 도착한다는 점.** CORS는 요청을 막는 게 아니라, 서버가 만든 응답을 브라우저가 화면에 전달하기 직전에 가로막는 것이다. 그래서 서버 로그에는 정상 처리로 남는데 프론트 화면에는 아무것도 안 뜨는 상황이 생긴다.

그리고 허용 여부는 오직 서버가 보내는 헤더로 결정되므로, **CORS 에러의 원인은 항상 백엔드에 있다.**

### Same-Origin과 Same-Site의 차이

| | Same-Origin | Same-Site |
| --- | --- | --- |
| 기준 | 프로토콜 + 호스트 + 포트 전부 일치 | 등록 가능 도메인만 일치 |
| 느슨한 정도 | 엄격 | 느슨 (포트·서브도메인 달라도 OK) |
| 쓰이는 곳 | "이 응답을 JS가 읽어도 되는가" → CORS | "이 요청에 쿠키를 실어 보낼까" → 쿠키 SameSite 속성 |

### WebConfig

```java
// config/WebConfig.java
package com.umc.movie.config;

import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.CorsRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**") // 모든 경로에 대해
                .allowedOrigins("http://localhost:5173") // 이 출처에서 오는 요청만 허용
                .allowedMethods("GET", "POST", "PATCH", "DELETE")
                .allowedHeaders("*");
    }
}
```

| 설정 | 의미 |
| --- | --- |
| `addMapping("/**")` | 우리 서버의 모든 URL에 적용 |
| `allowedOrigins(...)` | 누구를 믿을지 |
| `allowedMethods(...)` | 어떤 HTTP 메서드를 허용할지 |
| `allowedHeaders("*")` | 어떤 요청 헤더든 받겠다 |

컨트롤러마다 `@CrossOrigin`을 붙이는 방법도 있지만, 서비스 전체에 같은 정책을 적용할 때는 한 곳에서 설정하는 쪽이 유지보수에 낫다고 판단했다.

## 7. 트러블슈팅

### ⚡ 이슈 No.1 — build.gradle.kts에 Groovy 문법을 붙여넣어 빌드 실패

**이슈**
Gradle 동기화 시 `Unexpected tokens (use ';' to separate expressions on the same line)` 에러가 4개 발생했다.

**문제**
IntelliJ의 New Project로 프로젝트를 만들면서 Gradle DSL을 Kotlin으로 골라 `build.gradle.kts`가 생성됐는데, 워크북 코드는 Groovy 문법이었다. 두 DSL은 문법이 다르다.

| 파일 | 문법 |
| --- | --- |
| `build.gradle` (Groovy) | `id 'java'`, `group = 'com.umc'` |
| `build.gradle.kts` (Kotlin) | `id("java")`, `group = "com.umc"` |

게다가 Spring Initializr가 아닌 일반 Java 프로젝트로 만들어서 `MovieApplication.java`도, `application.yml`도 없는 상태였다.

**해결**
프로젝트를 지우고 IntelliJ의 **Spring Boot 제너레이터**로 다시 만들었다. 타입을 **Gradle - Groovy**로, Java를 **21**로, 구성을 **YAML**로 지정했다.

### ⚡ 이슈 No.3 — 비밀번호가 맞는데 Access denied

**이슈**
서버 실행 시 아래 에러로 기동이 실패했다.

```
SQL Error: 1045, SQLState: 28000
Access denied for user 'root'@'localhost' (using password: YES)
```

**문제**
`using password: YES`라서 비밀번호는 전달되고 있었다. Workbench에서는 같은 계정·같은 비밀번호로 잘 접속됐기 때문에 한참 헤맸다.

원인은 **포트**였다. 이 PC에는 MySQL이 두 개 떠 있었고, Workbench 연결은 **3307**인데 `application.yaml`은 기본값인 **3306**을 보고 있었다. 3306에도 다른 인스턴스가 응답하고 있어서 "서버는 있는데 비밀번호가 틀리다"로 나타난 것이다.

**해결**
Workbench 연결 카드에서 실제 포트를 확인하고 `application.yaml`을 고쳤다.

```yaml
url: jdbc:mysql://localhost:3307/umc_movie
```

**배운 점**
`Access denied`를 비밀번호 문제로만 단정하면 안 된다. 포트가 다르면 아예 다른 DB 서버에 접속을 시도하게 된다. 접속 정보는 호스트·포트·계정·비밀번호를 한 세트로 확인해야 한다.

### ⚡ 이슈 No.5 — 간이 프론트에서 ERR_CONNECTION_REFUSED

**이슈**
CORS 설정을 마쳤는데도 Console에 에러가 떴다.

```
Failed to load resource: :3000/members/nickname/noco
net::ERR_CONNECTION_REFUSED
Uncaught (in promise) TypeError: Failed to fetch
```

**문제**
워크북이 제공한 `index.html`이 NestJS 기준(3000번)으로 작성돼 있었다. 나는 Spring(8080)이라 3000번에는 아무것도 떠 있지 않았다. **CORS 에러가 아니라 요청이 출발도 못 한 상태**였다.

| | 이번 에러 | CORS 에러 |
| --- | --- | --- |
| 메시지 | `ERR_CONNECTION_REFUSED` | `blocked by CORS policy` |
| 서버 도달 | ❌ | ✅ |
| 서버 로그 | 안 남음 | 정상 처리로 남음 |

**해결**
`index.html`의 `localhost:3000`을 전부 `localhost:8080`으로 바꿨다.

**배운 점**
콘솔에 빨간 줄이 뜬다고 전부 CORS는 아니다. 에러 메시지를 먼저 읽어야 한다. CORS는 요청이 서버에 **도달한 뒤**에 생기는 문제라, 연결 자체가 거부되면 해당하지 않는다.

## 8. 핵심 키워드 정리

### SOP와 CORS

SOP는 브라우저가 "다른 출처로 간 요청의 응답을 JS가 읽지 못하게" 막는 기본 보안 규칙이고, CORS는 서버가 응답 헤더로 "이 출처는 허용한다"고 알려주어 그 제한을 푸는 장치다. 요청 자체는 서버에 도달하고 처리도 되지만, 브라우저가 응답을 화면에 넘기기 직전에 가로막는다는 점이 핵심이다.

### Same-Origin과 Same-Site의 차이

Same-Origin은 프로토콜·호스트·포트가 전부 같아야 하고, Same-Site는 등록 가능 도메인만 같으면 된다. 전자는 응답을 읽을 수 있는지(CORS), 후자는 쿠키를 자동으로 실어 보낼지를 판단할 때 쓰인다.

### 쿠키의 SameSite 속성

쿠키가 교차 사이트 요청에 실릴지를 정하는 속성으로 `Strict`, `Lax`, `None` 세 값이 있다. `None`으로 풀려면 `Secure`가 필수다. 정규 커리큘럼의 로그인은 헤더(JWT) 방식이라 이번에는 직접 건드릴 일이 없었다.

### 복합 UNIQUE 제약을 사용하는 이유

단일 컬럼으로는 표현할 수 없는 "조합의 유일성"을 보장하기 위해서다. `(member_id, movie_id)`에 UNIQUE를 걸면 한 사람이 같은 영화에 평점을 두 번 남기는 것을 DB가 막아준다. 애플리케이션 코드의 중복 검사만으로는 동시 요청이 들어올 때 둘 다 통과할 수 있는데, DB 제약은 그런 경우에도 확실히 막는다.

### 외부 Open API 연동 시 API Key는 어디에 두어야 안전한가

**백엔드다.** 프론트에 두면 브라우저 개발자 도구나 번들 파일에서 그대로 노출되고, 환경 변수로 넣어도 빌드 결과물에 문자열로 박힌다. 키가 유출되면 할당량이 소진되거나 요금이 청구될 수 있다.

다만 이번 프로젝트는 영화 목록·상세·검색을 프론트가 TMDB에서 직접 호출하는 구조다. TMDB의 읽기 전용 키는 공개를 전제로 발급되고 백엔드가 중계하면 불필요한 지연만 생기기 때문이다. 쓰기 권한이 있거나 과금되는 키라면 반드시 백엔드에 숨기고 프록시해야 한다.
